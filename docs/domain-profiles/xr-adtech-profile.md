# XR AdTech Domain Profile

Доменный профиль для `decision-intelligence-core`: связывает события XR-сессии
(телефон ↔ очки) с инвариантами ядра и криптографическим аудитом.

## 0. Честные рамки

- Ядро реализует **только** инварианты **I3, I4, I6, I7**. Профиль не вводит
  новых инвариантов и не обещает того, чего ядро не делает.
- Источник истины по событийному контракту —
  `schemas/xr-event.schema.json` (v1) в репозитории
  `LIGHTWEIGHT-XR-CONTENT-ENGINE`. Этот документ контракт не переопределяет,
  а описывает, как его события ложатся на примитивы ядра.
- Подключение профиля — через `runtime_context` ядра
  (`{"domain_profile": "xr-adtech-v1", ...}`), без изменений кода ядра.

## 1. Концепция

В XR AdTech единицей биллинга является не «показ пикселя на экране», а
**криптографически подтверждённое внимание (Proof of Attention)** —
без стриминга взгляда и видеокамер.

Телефон выступает доверенным edge-валидатором: считает агрегаты телеметрии
и отправляет события в ядро. Очки отдают только позу головы, дискретные жесты
и подтверждения; сырое видео и суставы руки за пределы очков не выходят.

## 2. Событийная модель

События (по `xr-event.schema.json` v1):

| Событие | Смысл |
|---|---|
| `PresetServed` | Старт отображения пресета (t=0). `trigger_type`: `schedule` \| `head_dwell` \| `phone_decision` |
| `ImpressionValidated` | Показ, прошедший физические условия контакта — **ключевое биллинговое событие** |
| `GestureInteraction` | Активное взаимодействие пользователя (жест из словаря) |
| `PresetClosed` | Завершение жизненного цикла пресета |

Конверт каждого события: `event_id`, `event_type`, `schema_version`,
`occurred_at_phone_ms` (телефон владеет часами — задержка транспорта
на проводе пренебрежима, на беспроводе фиксируется как известная погрешность),
`session_id`, `preset_id`, `evidence_refs` (обязан быть непустым).

Опционально: `PresetLoaded` (предзагрузка ассетов) — для воронки
«загружено → показано → валидировано» и отладки; на биллинг не влияет.

## 3. Проекция на примитивы ядра

Каждое XR-событие проецируется на `UpdateMetric`:

- `metric_name`: `xr.preset_served` / `xr.impression_validated` /
  `xr.gesture_interaction` / `xr.preset_closed`
- `value`: исход события (`SERVED`, `VALIDATED`, `TIMELINE_END`, …)
- `idempotency_key`: `event_id` из конверта (см. I6)
- `evidence_refs`: из конверта, как есть (opaque-указатели на on-device
  доказательства, напр. `dwell:preset_retail_spring_01:8200ms`)
- `runtime_context`: `{"domain_profile": "xr-adtech-v1",
  "session_id": …, "preset_id": …, "dwell_ms": …, "imu_v_max_mps": …}`

## 4. Маппинг на инварианты ядра

| Инвариант | Правило профиля | Результат при нарушении |
|---|---|---|
| **I3 (Evidence Boundary)** | `ImpressionValidated` не регистрируется как оплачиваемый без непустого `evidence_refs` | Метрика отклоняется (422 / `INVALID_ARGUMENT`) — «нет доказательства внимания, нет биллинга» |
| **I4 (Policy Safety)** | Финальный скор кампании/пресета не вычисляется без подтверждённых границ сессии (`PresetServed` + `PresetClosed`) | Политика возвращает `INSUFFICIENT_DATA`, частичный скор не публикуется |
| **I6 (Strict Idempotency)** | Дедупликация строго по `event_id` как `idempotency_key` | Повтор при ретрае сети → `DUPLICATE_IGNORED`, повторного списания нет |
| **I7 (Metric Superseding)** | Все события сессии дописываются в append-only Audit Trail и анкорятся в Merkle-дерево | Прошлые показы изменить/удалить невозможно; нарушение — Merkle-proof не сходится |

## 5. Правило биллинга (политика профиля, не ядра)

Показ считается оплачиваемым, если одновременно:

1. `dwell_ms >= 1200` — порог валидированного внимания;
2. `imu_v_max_mps <= V_MAX` — голова была относительно неподвижна
   (защита от «мотнул головой мимо контента»).

`V_MAX` — **настраиваемый параметр профиля**, устанавливается по датасету
жестов (Milestone 1). Значение `1.2 м/с` — плейсхолдер, не спецификация.

## 6. Расширение `PresetClosed` (уровень профиля)

- `reason`: `timeline_end` | `gesture_close` | `user_dismiss` | `error`
- `total_active_ms`: int — суммарное активное время пресета в сессии

## 7. Приватность

- Очки → телефон: поза головы + дискретные жесты + подтверждения.
  Сырое видео и сырые суставы руки за пределы очков не выходят.
- Телефон → ядро/аудит: агрегаты и `evidence_refs`.
- Дальше — только хэши и Merkle-корни (паттерн Defense-Dossier).

## 9. Чего профиль не делает

- Не меняет ядро и не добавляет инвариантов.
- Не использует трекинг глаз и динамическую окклюзию — статичное решение
  без трекинга глаз является архитектурным преимуществом
  (энергопотребление, приватность), а не временным компромиссом.
- Не хранит персональные данные: в ядро уходят только агрегаты,
  ссылки на доказательства и хэши.
